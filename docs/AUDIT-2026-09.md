# Audit IO BILL — 19 septembre 2026

Audit demandé sur quatre angles : risques métier, sécurité, robustesse
technique, qualité du code. Chaque constat a été vérifié dans le code. Les
points écartés après vérification sont signalés comme tels.

Contexte : un client payant en production, un développeur seul, Supabase en
plan gratuit, Vercel en plan Hobby — et **12 fonctions serverless sur 12**,
c'est-à-dire aucune marge.

---

## 0. LA CAUSE COMMUNE — Les helpers transforment un échec en donnée plausible

Les constats qui suivent ne sont pas douze problèmes indépendants. Ils
découlent presque tous d'une seule décision, prise une fois dans
`src/lib/supabase.js`, et répétée dans IO CAR : **quand une requête échoue,
le helper ne le dit pas — il renvoie une valeur qui ressemble à un résultat
normal.**

```js
async select(...) { ... return r.ok ? r.json() : []; }      // échec → liste vide
async insert(...) { ... return r.ok ? r.json() : null; }    // échec → null, sans lever
async update(...) { ... return r.ok ? r.json() : null; }    // échec → null, sans lever
```

Trois lignes, et deux conséquences qui traversent toute l'application.

### Une lecture échouée devient « il n'y a rien »

`sb.select` renvoie `[]` sur échec. Un jeton expiré, une coupure réseau, une
politique RLS qui refuse : dans les trois cas, l'appelant reçoit une liste
vide, exactement comme si la base était réellement vide. **105 appels** dans
l'application.

Le cas le plus coûteux est l'onglet TVA de la fiche client du cabinet. Il
charge les factures, les achats et les avoirs de la période, puis en calcule
la TVA collectée et déductible. Son état se résume à `periodData` : **il n'y
a aucun état d'erreur**, aucun `catch`, aucun message possible.

Si l'une des trois requêtes échoue, le comptable ne voit pas une erreur. Il
voit **0 €**. Et un zéro, sur un récapitulatif de TVA, ne ressemble pas à une
panne : il ressemble à un client qui n'a pas facturé ce mois-ci.

C'est le défaut le plus cher de l'application, parce qu'il ne produit pas un
plantage mais un chiffre faux, présenté avec la même assurance qu'un chiffre
juste, sur l'écran qui sert à établir une déclaration.

### Une écriture échouée ne laisse rien

`sb.insert` et `sb.update` renvoient `null` **sans lever d'exception**. Un
appelant qui ne teste pas le retour — et il y en a dix-sept — croit avoir
écrit. C'est le mécanisme détaillé au point 1 ci-dessous, et c'est déjà
exactement ce qui s'était produit le 12 septembre avec les lignes d'avoir.

### Pourquoi c'est une bonne nouvelle

Parce que le correctif est concentré. Il ne s'agit pas de reprendre 120
appels, mais de faire dire la vérité à **trois fonctions** : lever une erreur
explicite sur `!r.ok`, et laisser les appelants décider quoi en faire.

Le travail réel est ensuite de reprendre les appelants qui comptaient sur le
silence — ceux qui affichent `[]` comme « aucun résultat » doivent afficher
« chargement impossible ». Mais c'est un travail borné, qu'on peut mener
écran par écran en commençant par ceux où un chiffre faux coûte quelque
chose : le récapitulatif TVA, le tableau de bord du cabinet, les totaux de
période.

## 1. ÉLEVÉ — Des factures peuvent être enregistrées sans leurs lignes

`sb.insert` et `sb.update` ne lèvent pas d'exception quand PostgREST refuse
l'écriture. Ils renvoient `null` :

```js
async insert(token, table, data) {
  const r = await fetch(...);
  return r.ok ? r.json() : null;   // ← ne lève jamais
}
```

Dix-sept appels d'écriture ignorent ce retour. Trois d'entre eux portent sur
`document_lines`, et ce sont les plus graves :

| Fichier | Ligne | Conséquence d'un refus |
|---|---|---|
| `InvoiceEditorModal.jsx` | 242 | Facture enregistrée **sans aucune ligne** |
| `CreditNoteEditorPage.jsx` | 343 | Avoir enregistré **sans aucune ligne** |
| `QuotesListPage.jsx` | 388 | Devis converti en facture **sans lignes** |

```js
if (linesPayload.length > 0) {
  await sb.insert(token, "document_lines", linesPayload);   // retour ignoré
}
```

Si l'insertion est refusée — RLS, colonne inconnue, contrainte `NOT NULL` —
le document est créé, l'utilisateur voit une réussite, et il ne reste qu'un
en-tête sans détail. Un tel document viole la règle **BR-16** d'EN 16931 (au
moins une ligne) et serait rejeté à la transmission, avec des totaux qui ne
correspondent à aucune ligne.

**Ce n'est pas théorique : c'est exactement le bug corrigé le 12 septembre
dans `api/public.js`**, où les lignes d'avoir poussées par IO CAR ne
s'écrivaient jamais à cause de trois violations simultanées, sans que le
résultat soit vérifié. La correction a été appliquée à ce chemin-là ; les
trois chemins ci-dessus portent toujours le même défaut.

**Correctif** : vérifier le retour et annuler ou signaler l'enregistrement.
Le meilleur endroit est le helper lui-même — faire lever `sb.insert` et
`sb.update` sur `!r.ok` corrigerait les dix-sept appels d'un coup, mais
demande de vérifier que les appels déjà protégés par un `try/catch`
« best-effort » (l'insertion dans `payments`, par exemple) se comportent
toujours comme voulu.

## 2. MOYEN — Un duplicata obsolète d'un endpoint serveur dans l'arbre client

`src/api/firm-invitation.js` est une copie **898 lignes** d'un endpoint
serveur qui en compte aujourd'hui **1 388**. Elle lit
`process.env.SUPABASE_SERVICE_ROLE_KEY` et vit dans `src/`, c'est-à-dire dans
l'arbre source du bundle navigateur.

**Ce n'est pas une fuite aujourd'hui, et je l'ai vérifié plutôt que supposé :**

- le fichier n'est importé par aucun code client, donc Vite ne l'inclut pas ;
- la chaîne `SUPABASE_SERVICE_ROLE_KEY` n'apparaît dans aucun fichier du
  bundle publié ;
- aucun JWT portant `role: service_role` n'apparaît dans le bundle (vérifié
  en décodant tous les JWT présents).

Mais c'est un piège à deux détentes. Un import ajouté par distraction, ou un
passage de `process.env` à `import.meta.env.VITE_*` pour « faire marcher »
ce fichier, exposerait la clé qui contourne toute la RLS. Et entre-temps,
490 lignes de retard en font une référence trompeuse pour qui l'ouvre en
croyant lire l'endpoint réel.

**Correctif** : le supprimer. Le vrai endpoint est `api/firm-invitation.js`.

## 3. MOYEN — Aucune marge sur les fonctions serverless

12 sur 12. Le plan Hobby refuse le déploiement au-delà, et **l'échec est
global** : il emporte le site entier, pas seulement la route ajoutée. C'est
arrivé le 10 septembre.

Cette contrainte a déjà façonné l'architecture, plutôt bien d'ailleurs :
`api/stripe.js` fusionne checkout et webhook en aiguillant sur la présence du
header `stripe-signature`, et la sauvegarde quotidienne a été greffée sur
`api/cron-reminders.js` au lieu d'avoir sa propre route.

Mais toute fonctionnalité future qui demande un endpoint — un webhook SumUp,
un rappel Wero, une intégration de paiement — se heurtera au mur. Deux
issues, à décider avant d'en avoir besoin dans l'urgence : fusionner deux
routes derrière un paramètre `action`, comme le fait déjà `api/admin.js`, ou
passer Vercel en plan Pro.

## 4. MOYEN — Quatre fichiers de tests qui ne tournent jamais

`tests/01-auth.spec.js`, `02-client-quote`, `03-invoice`, `04-public`
existent. Mais `package.json` ne déclare **aucun script `test`**, et il n'y a
aucun workflow GitHub Actions dans les deux dépôts.

Ces tests ne s'exécutent donc jamais — ni en local par commodité, ni avant
un déploiement. Le travail est fait, il ne sert pas.

Remettre un script `test` et les faire tourner est peu coûteux. Encore
faut-il vérifier d'abord qu'ils passent : quatre fichiers écrits il y a
plusieurs mois sur une base qui a beaucoup bougé ont toutes les chances
d'être périmés. Un test rouge qu'on ignore est pire que pas de test.

## 5. FAIBLE — Deux vulnérabilités modérées sur React Router

`npm audit` signale deux avis sur React Router :

- **Redirection ouverte** via un antislash dans `<Link>` et `useNavigate`
  (contournement de CVE-2025-68470). Applicable à une application de type
  SPA comme celle-ci, dans la mesure où une cible de navigation pourrait
  provenir d'une donnée non maîtrisée.
- **Injection de constructeur** via `deserializeErrors()` à l'hydratation
  SSR. IO BILL ne fait pas de rendu serveur, cet avis ne s'applique donc
  probablement pas.

Le correctif passe par `npm audit fix --force`, qui implique un changement de
version majeure. À traiter comme une mise à jour planifiée, pas dans
l'urgence — mais à ne pas laisser traîner indéfiniment non plus.

## 6. QUALITÉ — Concentration dans quelques gros modules

L'architecture modulaire d'IO BILL est saine — 99 fichiers, 32 000 lignes,
des responsabilités séparées. Mais cinq fichiers concentrent le quart du
code :

| Fichier | Lignes |
|---|---|
| `core/SettingsPage.jsx` | 2 278 |
| `firm2/FirmClientFichePage.jsx` | 2 041 |
| `invoicing/InvoicesListPage.jsx` | 1 652 |
| `purchases/PurchasesPage.jsx` | 1 394 |
| `admin/AdminPage.jsx` | 1 006 |

`FirmClientFichePage.jsx` héberge à lui seul sept onglets et le générateur
PDF de l'annexe « Historique des paiements ». Ce dernier n'a rien à voir avec
l'affichage d'une fiche client : il se sortirait sans risque.

Rien d'urgent, et surtout rien à réécrire pour le plaisir. Mais ces fichiers
sont ceux où les prochaines fonctionnalités iront s'empiler.

## Points vérifiés et écartés

- **`api/firm-invitation.js` authentifie bien** ses appelants, via
  `getUserFromToken`. Une première lecture automatique l'avait signalé comme
  dépourvu d'authentification : c'est faux, le motif de recherche ne
  correspondait simplement pas.
- **Aucune clé `service_role` dans le bundle publié** (vérifié en décodant
  tous les JWT de `dist/assets/`).
- **Aucun `.env` versionné** sur toute l'histoire du dépôt.
- **Aucun `dangerouslySetInnerHTML`**, aucun `eval`, aucun `new Function`.
- **La RLS est active** sur toutes les tables portant `company_id`, avec des
  politiques `select`/`insert`/`update`/`delete` générées uniformément —
  c'est ce qui rend sûre la correction du moyen de paiement livrée hier.
- **La page « Historique des paiements » du comptable est reconstruite à
  chaque export**, sur une copie ; l'original transmis à la PDP n'est jamais
  modifié. Corriger un encaissement a posteriori est donc sans effet sur les
  documents archivés.

## 7. À VÉRIFIER — Les plafonds de chargement

Les écrans chargent leurs listes avec des plafonds explicites : `limit: 500`
(onze appels), `limit: 200` (onze), `limit: 50` (huit), `limit: 300`. Tant
que les volumes restent en dessous, aucun problème.

Deux points à surveiller à mesure que les données grossissent :

- Un écran qui **calcule un total** sur une liste plafonnée affichera un
  total faux dès le dépassement, sans rien signaler. L'onglet TVA, lui, ne
  pose pas de plafond — c'est le bon choix — mais il dépend alors du plafond
  serveur de PostgREST (`db-max-rows` dans les réglages Supabase), qui
  tronquerait tout aussi silencieusement. **À vérifier dans ton tableau de
  bord Supabase** : je n'y ai pas accès.
- L'historique des paiements d'un client est chargé avec `limit: 50`.

Rien d'urgent aujourd'hui. Mais ce sont des défauts qui n'apparaissent que le
jour où l'activité grandit, c'est-à-dire au pire moment.

## Vérifié et sain

- **Le pont IO CAR → IO BILL est idempotent** : la création d'entreprise est
  indexée sur `(source_app, external_ref)` et renvoie l'existant plutôt que
  de dupliquer. La signature de devis est également protégée contre le
  rejeu.
